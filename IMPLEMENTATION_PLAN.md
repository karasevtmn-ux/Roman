# План создания системы мониторинга дел ГАС «Правосудие» (Windows Desktop)

## 1) Оценка идеи: веб vs десктоп
Ваше предложение перейти на десктоп — **рациональное**. Если не хотите покупать домен и поддерживать веб-сервер, для MVP действительно лучше сделать Windows-приложение.

### Когда веб всё же нужен
Веб нужен, если:
- хотите удаленный доступ из любого места без установки;
- планируете расширять число пользователей;
- нужен «единый вход» через браузер.

### Когда лучше десктоп (ваш случай)
- нет желания тратить деньги на домен/SSL;
- нужен быстрый запуск на одном Windows-ПК для одного пользователя;
- допустима установка приложения на один рабочий ПК.

**Решение:** для следующих итераций принимаем **Desktop-first (Windows)**, но закладываем архитектуру, которую позже можно перенести в веб с поддержкой многопользовательского режима (добавление пользователей, роли и разграничение доступа).

---

## 2) Цель системы
Приложение для Windows, которое:
- принимает ссылки на карточки дел (Москва + остальные суды РФ);
- ночью по локальному времени суда проверяет изменения;
- сравнивает текущие данные с предыдущим снимком;
- отправляет email-уведомления при изменениях;
- отправляет отдельное уведомление, если ссылка перестала работать.

---

## 3) Рекомендуемый стек (десктоп)
- **Desktop UI:** Python + PySide6 (Qt) — полноценный интерфейс Windows.
- **Парсинг:** Playwright (Chromium в headless-режиме).
- **Хранилище:** SQLite (локальная БД, без отдельного сервера).
- **Планировщик:** APScheduler (локально в приложении/службе).
- **Email:** SMTP.
- **Упаковка:** PyInstaller (в `.exe` установщик/архив).

Почему так: минимальная и полностью бесплатная инфраструктура для MVP (без домена и платного хостинга), с низким порогом сопровождения.

---

## 4) Что понадобится (без программирования)
1. ПК/ноутбук с Windows 10/11.
2. Почтовые SMTP-данные для отправки уведомлений.
3. Email получателя уведомлений (один основной адрес).
4. Набор тестовых ссылок:
   - 5+ ссылок `mos-gorsud`;
   - 10+ ссылок `sudrf` из разных регионов.
5. Папка для резервных копий локальной БД.

---

## 5) Функциональные требования
1. Однопользовательский режим: вход в приложение не требуется.
2. Управление ссылками (добавить/изменить/удалить) с полями: Истец, Ответчик, Суд, Номер дела, Комментарий, Субъект РФ.
3. Два адаптера парсинга:
   - `mos-gorsud.ru`;
   - `*.sudrf.ru`.
4. Мониторинг изменений по блокам:
   - номер дела;
   - вкладки «Дело», «Движение дела», «Стороны по делу (третьи лица)»;
   - добавление/удаление вкладок;
   - добавление/удаление текста судебного акта.
   - учет особенностей источников: для `mos-gorsud` акты обычно публикуются во вкладке «Документы» (без добавления новой вкладки), для `sudrf` возможно появление новой вкладки.
5. Ночные проверки по timezone суда (timezone автоматически определяется по полю «Субъект РФ», с возможностью ручной правки).
6. Email-уведомления:
   - о любых изменениях;
   - с текстом судебного акта, если он добавлен;
   - о нерабочей ссылке;
   - с прямой ссылкой на карточку дела для быстрой проверки изменений.
7. История проверок и изменений в интерфейсе.

---

## 6) Как будет работать мониторинг
1. Приложение сохраняет ссылку и определяет тип суда.
2. Ночью запускает проверку в окне 01:00–05:00 по времени суда.
3. Парсер формирует нормализованный snapshot (JSON-структура).
4. Система сравнивает snapshot с предыдущим и строит diff.
5. При diff != пусто формирует событие и отправляет email.
6. При многократной ошибке доступа — помечает ссылку проблемной и отправляет письмо «обновите ссылку».

## 7) UX/UI: закладываем отдельный трек (обязательно)
В следующих итерациях делаем полноценный UX/UI-процесс.

### Что включаем в план
1. **UX-исследование (минимум):** сценарии пользователя и карта экранов.
2. **Wireframes:** черно-белые прототипы ключевых окон.
3. **UI-kit:** кнопки, таблицы, формы, статусы, уведомления.
4. **Интерактивный прототип:** проверка удобства до разработки сложных экранов.
5. **Дизайн-ревью перед каждой фазой разработки UI.**

### Ключевые экраны для проектирования
- Стартовый экран/дашборд;
- Дашборд ссылок;
- Добавление/редактирование ссылки;
- История изменений;
- Настройки SMTP и расписания;
- Поля карточки ссылки: Истец, Ответчик, Суд, Номер дела, Комментарий;
- (Опционально позже) поддержка нескольких профилей и пользователей при переносе в веб.

## 8) Фазы реализации (перезапуск с Фазы 0)

### Фаза 0 (перезапуск) — Согласование требований + UX-концепция
- Утверждаем обновленное ТЗ именно под Windows Desktop.
- Утверждаем критерии «что считается изменением».
- Утверждаем формат писем.
- Собираем тестовые ссылки.
- Делаем UX-артефакты уровня: user flow + wireframes v1.

### Фаза 1 — Технический каркас desktop-приложения
- Каркас PySide6-приложения.
- Локальная БД SQLite.
- Локальные настройки приложения (без авторизации).

### Фаза 2 — Управление ссылками
- CRUD ссылок.
- Валидация URL и типа суда.
- Хранение ссылок в едином списке одного пользователя.

### Фаза 3 — Парсинг (2 адаптера)
- Реализация адаптера Москвы.
- Реализация адаптера регионов.
- Логи ошибок парсинга.

### Фаза 4 — Snapshot + Diff + История
- Сохранение снимков.
- Вычисление изменений.
- Вывод истории изменений в UI.

### Фаза 5 — Планировщик и часовые пояса
- Ночной запуск по timezone суда (окно 01:00–05:00).
- Интервал повторных проверок при ошибках: 30 минут.
- Статус «проблемная ссылка» после 3 неудачных проверок подряд.

### Фаза 6 — Email-уведомления
- SMTP-интеграция.
- Шаблоны писем по событиям.
- Вложение/вставка текста судебного акта в письмо.

### Фаза 7 — UX/UI polishing + пилотный запуск
- Улучшение интерфейса после обратной связи.
- Упаковка в `.exe`.
- Пилот на рабочем ПК пользователя.
- Вариант для проверок при выключенном ПК: вынос фонового модуля на отдельный всегда-включенный Windows-ПК/мини-ПК в локальной сети (без домена).
